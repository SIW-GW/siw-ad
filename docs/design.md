# SIW AD 詳細設計案

更新日: 2026-11-11

[初期構想案](./initial-concept.md)に基づく初期版の設計。ローカル実装ではHTML/CSS/JavaScriptとNode.js 24.22.1の標準機能を採用し、外部パッケージは追加しない。GitHubでの公開は別作業。[登録・設置・運用手順](./usage.md)も参照する。

## 1. 全体構成

```text
作者 → PR（JSON・画像）→ 自動検証 → レビュー・マージ
                                               ↓
                                      ビルド → GitHub Pages
                                               ↓
各アプリ → iframeの読み込み → 公開JSONの取得 → 抽選 → 紹介カード
```

広告データの正本はGitリポジトリ。ビルド時にアプリごとのJSONをまとめ、広告表示ページと同じ配信元から公開する。閲覧のたびにGitHub APIへアクセスしない。

抽選は各閲覧者のブラウザで行う。広告配信API、データ更新API、永続化サーバーは設けない。

## 2. ディレクトリ構成案

```text
ads/                     # 1アプリにつき1つのJSON
  app-a.json
  app-b.json
images/                  # 登録画像
  app-a.webp
  app-b.webp
src/                     # 表示ページのソース
scripts/                 # 検証・データ集約・ビルド
docs/                    # 設計・運用・利用ガイド
.github/workflows/       # PR検証とPages配信
dist/                    # 生成物。Gitにはコミットしない
  index.html             # サービス説明と埋め込み方法
  embed/index.html       # 広告表示ページ
  assets/                # JavaScript・CSS・画像
  ads.json               # 集約した配信用データ
  site.json              # 本番／デモの表示区分
```

`docs/`は設計文書の置き場とし、Pagesの公開ソースにはしない。`dist/`のみを配信し、リポジトリ全体を公開成果物に含めない。Node.jsのスクリプトで検証・集約・コピーを行い、フレームワークは使用しない。`examples/`のサンプルはデモ用の`.preview/demo/`にだけ出力する。初回掲載作品として、作者から登録依頼を受けたQHandを本番の`ads/`に登録する。

## 3. 広告データ

`ads/app-a.json`の例:

```json
{
  "id": "app-a",
  "name": "アプリA",
  "description": "学校の予定を共有できるアプリです。",
  "url": "https://example.com/",
  "image": "images/app-a.webp",
  "enabled": true
}
```

| 項目 | 型 | ルール |
| --- | --- | --- |
| `id` | string | 必須。一意。2〜64文字。小文字英数字と単語間のハイフン。ファイル名の拡張子を除いた部分と一致 |
| `name` | string | 必須。空白のみは不可。前後の空白なし。1〜60文字 |
| `description` | string | 必須。空白のみは不可。前後の空白なし。1〜140文字。プレーンテキスト |
| `url` | string | 必須。絶対HTTPS URL。ユーザー名・パスワードを含めない |
| `image` | string | 必須。`images/`配下の既存ファイルを指すリポジトリ相対パス |
| `enabled` | boolean | 必須。`true`で配信候補、`false`で候補から除外 |

文字数はUnicodeコードポイント数で数える。未知の項目は入力ミスとしてエラーにする。`id`の形式は`^[a-z0-9]+(?:-[a-z0-9]+)*$`とする。

IDは表示名やURLが変わっても維持する。変更すると設置済みの埋め込みURLに影響するため、原則変更しない。同じアプリを重複登録しない運用とし、別IDでの重複はレビューでも確認する。

画像はPNG・JPEG・WebP、1ファイル500 KiB以下を初期上限とする。推奨比率は16:9だが、横長バナーの画像領域では正方形にトリミングする。画像内に重要な説明文を詰め込まず、カードのテキストで内容を伝える。SVGや外部画像URLは受け付けない。

## 4. 配信用データ

ビルド時に全レコードを検証したうえで、有効な広告だけを`ads.json`に出力する。

```json
{
  "schemaVersion": 1,
  "registeredAppIds": ["app-a", "app-b"],
  "ads": [
    {
      "id": "app-a",
      "name": "アプリA",
      "description": "学校の予定を共有できるアプリです。",
      "url": "https://example.com/",
      "image": "assets/images/app-a.webp"
    }
  ]
}
```

- `registeredAppIds`には掲載停止中も含める。自分の広告を停止していても、他のアプリの紹介は継続できるようにする。
- `ads`は`enabled: true`のみ。`enabled`は配信用には出力しない。
- ID順に並べ、同じ入力から同じ結果を生成する。
- 画像はビルド時に配信先のパスへコピーし、出力JSONもそのパスに変換する。
- `schemaVersion`が未対応の場合、表示側は抽選せずエラー時の案内を表示する。

サイトのベースURLを基準にデータ・画像のURLを解決する。`/ads.json`のようなドメイン直下固定のパスにせず、GitHub Pagesの`/siw-ad/`配下でも動作させる。

## 5. 埋め込みインターフェース

標準のプロジェクトPagesを利用する場合の想定URL:

```text
https://siw-gw.github.io/siw-ad/embed/?app=app-a
```

実際の公開URLはPages設定後に確認する。`app`は広告枠を設置するアプリの登録IDとし、1つだけ指定する。同じアプリ内の複数ページで同じIDを使ってよい。

```html
<iframe
  src="https://siw-gw.github.io/siw-ad/embed/?app=app-a"
  title="コミュニティのアプリ紹介"
  width="320"
  height="72"
  loading="lazy"
  referrerpolicy="no-referrer"
  style="display: block; width: 100%; max-width: 720px; margin-inline: auto; border: 0;"
></iframe>
```

初期版は画面下に置く横長バナー1種類とし、横幅280〜720px・高さ72pxを表示保証の対象にする。左に64px幅の画像、右にラベル・名前・紹介文を並べる。名前・紹介文はそれぞれ1行で省略し、リンクにはアプリ名と紹介文の全文を含むアクセシブルな名前を付ける。画像は装飾扱いの`alt=""`とする。親ページとの高さ通知は扱わない。

案内ページでは画面下への固定を初期選択とし、固定用asideと本文末尾の余白を含むコードを生成する。高さ72pxと`safe-area-inset-bottom`の領域を確保し、iframe自体は親画面を操作しない。通常配置のiframeだけを生成することもできる。設置元にボトムナビなどがある場合の位置・余白・重なり順は設置元で調整する。プレビューは設置先アプリの下部にバナーがある状態を示す。

案内ページのデモは、設置するアプリの選択に関係なく、掲載中の全作品からランダムに1件を描画する。実際のiframeと同じバナー描画処理を使い、実際の配信では自分の作品が除外されることを注記する。停止中の作品は表示しない。埋め込みURLや配信時の抽選条件は変更せず、コピーするコードにもデモ用の例外を含めない。候補が2件未満の場合、再抽選ボタンは無効にする。

アプリ選択・固定表示の切り替え・コードのコピーは、初期表示では閉じた設置用ダイアログにまとめる。「自分のアプリに設置する」で開き、閉じるボタンまたはEscキーで閉じる。デモの抽選とコード生成は独立して動作する。

広告カードには「コミュニティのアプリ紹介」と表示し、設置元自身の機能との区別を付ける。リンクは利用者の操作で新しいタブに開き、`rel="noopener noreferrer"`を付ける。

設置先にCSPがある場合は、配信元を`frame-src`で許可する必要がある。HTMLの埋め込みができないサービスは初期版の対象外。利用ガイドでは、動作する埋め込みコードと必要な設定をまとめる。

`app`は自己申告であり、設置元を認証する値ではない。URLの書き換えを防いだり、登録したサイト以外からの埋め込みを拒否したりする機能は設けない。

## 6. 表示処理と状態

1. `app`が1つだけ指定され、形式が正しいか確認する。
2. 同じ配信元の`ads.json`を読み込む。タイムアウトは10秒とする。
3. スキーマと最低限のデータ構造を検証し、`app`が`registeredAppIds`に存在するか確認する。
4. 有効な広告から`id === app`のレコードを除外する。
5. 残った候補から各候補が同じ確率になるように1件選ぶ。
6. 画像・名前・紹介文・リンクをカードに反映する。

ページ読み込みごとに1回抽選する。自動ローテーション・定期再取得・自動再試行は行わない。前回の表示結果は保存しないため、続けて同じ広告が選ばれることもある。

| 状態 | 表示・動作 |
| --- | --- |
| 読み込み中 | 大きさを保った読み込み案内を表示 |
| 正常・候補あり | 1件のカードを表示 |
| 候補なし | 「紹介できるアプリはまだありません」 |
| `app`未指定・重複・形式不正・未登録 | 「広告枠の設定を確認してください」。抽選しない |
| 通信失敗・タイムアウト・データ不正 | 「紹介を読み込めませんでした」。壊れたリンクは表示しない |
| 選ばれた画像の読み込み失敗 | 固定の代替表示を使い、アプリ名・紹介文・リンクは維持 |

紹介カードを挿入する際に、登録文字列をHTMLとして解釈しない。リンクもHTTPSなどの条件を表示時に再確認する。外部のページ内容やOGPを閲覧時に取得しない。

等確率の抽選は、全アプリの表示回数が均等になることを保証しない。初期版には配信実績の保存もないため、均等配信やクリック数を要件にしない。

## 7. PRと掲載ライフサイクル

| 操作 | データ変更 | 公開への影響 |
| --- | --- | --- |
| 登録 | 新しいJSON・画像を追加 | マージと配信成功後に候補へ追加 |
| 更新 | 同じIDの内容・画像を編集 | 配信成功後の新しい読み込みから反映 |
| 停止 | `enabled: false`に変更 | 配信成功後の新しい読み込みから候補除外 |
| 再開 | `enabled: true`に変更 | 配信成功後に候補へ復帰 |

初期版では停止したレコードを残し、IDを再利用しない。広告の承認状態は別フィールドで持たず、PRのレビューとマージを承認の記録とする。申請者がコミュニティのメンバー・作品関係者かは管理者が確認し、メンバー照合用APIや独自アカウントは設けない。

ビルドや配信が失敗した場合は公開中の旧版が継続する。停止PRのマージだけで停止完了とはせず、Actionsの成功と公開データからの除外を確認する。すでに開かれたページやキャッシュには旧広告が残る可能性があるため、即時停止は保証しない。

作者に変更を依頼する場合も、管理者が代理修正する場合も、PR上に理由を残す。緊急時は管理者が停止PRを優先して処理する。機密情報を誤登録した場合の履歴削除は、通常の掲載停止とは別の対応とする。

## 8. 自動検証

PR時と配信用ビルド時に同じ検証処理を使い、失敗したファイル名・項目・理由を表示する。

| 対象 | 検証内容 |
| --- | --- |
| JSON | パース可能、必須項目、型、未知の項目、文字数 |
| ID | 形式、長さ、一意性、ファイル名との一致 |
| URL | 絶対HTTPS URL、認証情報なし、localhostやIPアドレスを登録しない |
| 画像パス | `images/`配下、親参照・絶対パス・シンボリックリンク不可、対象ファイルあり |
| 画像ファイル | 拡張子とPNG・JPEG・WebPのヘッダー等の一致、500 KiB以下。完全な画像デコード検証ではない |
| 集約データ | スキーマ、ID参照、出力先画像の存在 |
| ビルド成果物 | 説明ページ・埋め込みページ・JSON・参照ファイルの存在 |

停止中のレコードも入力データとして検証する。外部URLへの通信による到達性チェックは必須CIにしない。通信障害やログイン制限に左右されるため、リンク先が紹介内容と合うか、一般利用者が利用できるかはレビューで確認する。

## 9. CIと配信

- PR: 読み取り権限で検証とビルドを実行する。配信は行わない。
- デフォルトブランチへの反映: 再検証・ビルドに成功した成果物のみPagesへ配信する。
- 配信ジョブ: `pages: write`と`id-token: write`を付与し、`github-pages`環境を使う。
- 権限はジョブに必要な範囲へ限定し、PR由来のコードに配信用権限を渡さない。
- 並行配信を制御し、古いコミットの成果物で後から上書きしない。
- 手動再実行・復旧手順を用意し、公開データがどのコミット由来かActionsのデプロイ記録で追えるようにする。

GitHub ActionsによるPagesの配信構成は[公式ドキュメント](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)に従う。手動入力の長期アクセストークンをフロントエンドへ埋め込まない。

運用開始時にはPRレビューと検証をマージ条件にするブランチ保護を推奨する。現在設定済みとはみなさず、Pagesの有効化と併せて別途設定・確認する。

## 10. 公開範囲とデータ収集

ソース、登録データ、画像、PR、履歴はpublicである。登録者向けに、公開用の文章・画像・URLだけを入れることを説明する。作者のメールアドレス、認証情報、学籍番号などはデータ項目として設けない。

アプリ側でCookie・ローカルストレージ・アクセス解析を使わず、表示回数やクリック数も独自には送信・保存しない。ただし、広告枠の取得は配信先への通信を伴い、リンクのクリック後は移動先への通信になる。ホスティング側のアクセス処理まで存在しないとは説明しない。

登録画像は同じ配信元から表示する。任意のHTML・JavaScript・外部トラッキング画像は受け付けない。

## 11. 実装時の検証項目

| 分類 | 確認すること |
| --- | --- |
| データ検証 | 正常データ、不足項目、型違い、ID重複、危険なURL、存在しない画像、不正パスを判定できる |
| 抽選 | 自分自身・停止中の広告を除外し、候補0件・1件・複数件を扱える |
| 抽選の境界 | 乱数の入力を固定して各候補を選べる。確率の偶然に依存するテストにはしない |
| エラー | 不正な`app`、JSON取得失敗、未対応スキーマ、画像失敗に対する表示がある |
| パス | ドメイン直下ではなく`/siw-ad/`配下でもJSON・画像を解決できる |
| ブラウザ | 別の配信元からiframeを埋め込み、ログアウト状態・スマートフォン幅で表示とリンクを確認する |
| 操作性 | キーボードでリンクへ移動でき、フォーカスが見え、名前と紹介文を読み取れる |
| 公開後 | 配信成功、公開JSON、別アプリへの遷移、停止反映を実際のPagesで確認する |

`.nvmrc`と`package.json`でNode.js 24.22.1を固定する。`npm run check`でデータ検証・Node.js標準テスト・本番ビルドを実行し、CIでも同じコマンドを使う。lint・TypeScript型チェックは未導入。ブラウザ・CI・公開後の検証結果は、それぞれ別の証拠として扱う。

## 12. 実装の順序

1. ランタイムと最小のビルド方法を決定し、バージョン・コマンドを明記する。
2. データ形式・検証処理と、2件以上の確認用データを用意する。
3. データ集約と埋め込みページを実装し、抽選・例外表示を確認する。
4. PR検証とPages配信のワークフロー、登録・設置・停止手順を用意する。
5. 設定作業と公開が依頼された段階でPagesを有効化し、公開後の完成条件を確認する。

公開先URL、レビュー担当者、ブランチ保護の具体的設定は運用開始前に確定する。独自ドメイン、表示形式の追加、計測、配信回数の調整は初期版の完成後に必要性を判断する。
